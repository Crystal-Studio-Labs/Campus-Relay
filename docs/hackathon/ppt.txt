## 2.1 What Campus Relay is (say it in one line)
Campus Relay is a working software system — not a slide-only idea. It is one
operating layer for everyday college work, built on ONE case engine with
policy, workflow, approval, SLA and audit stages; plus offline-first
Progressive Web App (PWA) clients, a gate-pass desk, notice broadcasting,
campus services (leave, library, fees, clearance, career, HR, feedback) and
attendance/marks that stay inside the class group.

Every campus request — a broken washroom tap, a bonafide certificate for a
loan, a hostel leave pass, a mess complaint — is one thing: a CampusCase.
Everything else is a reusable engine that works on it: policy → workflow →
approval → SLA → assignment → notification → resolution → requester check →
audit. Adding a new campus service is SETUP (a catalogue entry, a workflow
and plain policy rules), not a new module.

The problem statement's four focus areas are all in the code:
  (1) hostel & facility maintenance,
  (2) gate security & curfew rules,
  (3) official broadcasts & circulars,
  (4) offline work when the network is down.

## 2.3 The problem it fixes (told as observations — no numbers)
- Repair requests sit in paper registers and separate department queues.
- Notices spread in chat groups with no proof that anyone read them.
- Gate passes are paper slips with no check and no control on way out and back.
- Weak network and few phones leave some students out.
- Split processes mean no clear owner, no SLA view, no audit trail, and
  papers that the person receiving them cannot check as real.
Result: no owner, no time target, no record — and the least-connected
students get the worst service.
IMPORTANT: the repository holds no survey or source for these points. Show
them as gaps you observed. Do NOT add a percent, a rupee figure or a
"days saved" number.

## 2.4 Core workflows (backed by code)
- Hostel repair: QR/form intake → policy check → routing → SLA → fix →
  REQUESTER check (staff cannot close it alone).
- Leave & gate: leave request → warden approval → digital gate pass →
  out and back check with clear refusal reasons.
- Offline: local IndexedDB outbox → network returns → idempotent replay
  (a replayed action returns the earlier saved result — no double work).
- Documents: request → policy/eligibility check → approval → PDF with QR and
  serial number → open PUBLIC check link that shows only valid or not valid.
- Notices: chosen audience → delivery → read and acknowledgement counts.

- Offline data: IndexedDB (native promised wrapper), client outbox, saved reads.
- Styling: layered CSS custom-property tokens (tokens → base → components →

- Backend: FastAPI, Uvicorn, Pydantic v2 + pydantic-settings.
- ORM / DB: SQLAlchemy 2.0, PostgreSQL 16, psycopg 3.
- Migrations: Alembic (6 revisions).
- Auth: PyJWT (HS256), bcrypt password hashing.
- Documents: ReportLab (PDF), qrcode.
- Tests: pytest + httpx TestClient, pytest-asyncio.
- CI: GitHub Actions — Postgres 16 service → migrate → seed → pytest;
  frontend npm ci → typecheck → build.
- Hosting plan (set up, live status NOT checked): Render (API), Vercel
  (frontend), Supabase (PostgreSQL).

## 3C. SIMPLE-LANGUAGE RULE (why: big words can be used against the team)
- Write for a smart 15-year-old. Short lines. One idea per line.
- Max about 10–12 words per slide line. Move detail to speaker notes.
- NO fancy words. Say it plain:
    use not utilise/leverage · help not facilitate · strong not robust ·
    smooth not seamless · set up not implemented · look at not examine ·
    clear not transparent · change not transform · start not initiate ·
    end not conclude · fast not rapid · plan not strategy ·
    fix not remediate · check not validate (unless testing data) ·
    ask not inquire · buy not procure · show not demonstrate.
- NO hype words at all: game-changer, world-class, cutting-edge, next-gen,
  revolutionary, unmatched, unstoppable, seamless, magical, 24/7, bulletproof.
- NO absolute words: always, never, 100%, guaranteed, best, first, only,
  impossible, unbreakable, unique, everyone, nobody. A judge can attack any
  of these in one question.
- NO unsure words either: we believe, we think, maybe, kind of. State simple
  checked facts plainly.
- Keep real product terms (PWA, SLA, audit trail, anti-passback, RBAC) ONLY
  when they matter, and add 3–6 plain words the first time:
    SLA = "a time limit for each request",
    audit trail = "an unchangeable record",
    anti-passback = "one pass cannot be used twice in a row",
    offline-first = "works without internet and syncs later",
    RBAC = "each role sees only what it should".
- Talk like a person, not a brochure. The spoken script in Part 5 must sound
  natural when read aloud.

## 3D. WHAT MAKES A DECK LOOK LAUGHABLE — NEVER DO THESE
A judging panel sees 20+ decks. Most get laughed at for polish and honesty
fails, not for weak ideas. Hard rules:
- NO emoji, clipart, cartoons, stock photos of random people, or fake logos.
- NO "AI-generated" look: purple-blue gradients, glowing borders, sparkle
  icons, random neon colours, shapes that serve no meaning. Every colour
  comes from the Part 4 token table, nothing else.
- NO leftover template text anywhere: "Click to add title", "Lorem ipsum",
  "Your text here", slide-number watermarks, theme placeholders, sample
  charts with fake data. The ONLY allowed bracket text is the demo URL.
- NO spelling mistakes. Run a spellcheck on the whole deck. All six team
  names, the team ID and the leader name must match Part 1 letter for
  letter — a misspelled name on the cover is the fastest way to lose a room.
- NO number style clashes: write counts the same way everywhere
  (145 tests · 185 handlers · 60 tables). One format, all 8 slides.
- NO reading the slide aloud. The slide is a cue; the speaker adds the
  story. A slide with more than ~30 words or more than 6 bullet lines is a
  fail — cut it, do not shrink the font.
- NO tiny text: nothing below 11pt, nothing a person at the back cannot read.
- NO overlapping arrows, labels colliding with text, or diagrams that only
  make sense with someone explaining them. Check at full-screen presenter
  view before the round.
- NO fake product screens. If no confirmed screenshot exists, show the
  marked placeholder box — a drawn fake UI caught by one judge ends the
  team's credibility.
- NO self-sabotage lines while speaking: never say "we had no time",
  "sorry", "this is incomplete", "we don't know how that works". Say what IS
  done, then what is NEXT (Slide 8 model). Never claim the code was built
  in 36 hours — Part 2 says it predates the hackathon, and one judge who
  checks the repo dates will catch it.
- The 5-SECOND TEST for every slide: if a judge who only glances at it for
  5 seconds still gets the point from the headline alone, the slide works.
  If not, rewrite the headline — do not add more text.
