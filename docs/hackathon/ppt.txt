SLIDE 2 — THE PROBLEM
--------------------------------------------------------------------
Headline:   CAMPUS OPERATIONS ARE FRAGMENTED
Sub-head:   The work happens where the network, the process and the person
            all break down.

Body — five short lines, each with a small icon (paper/register, chat/WhatsApp,

  • Nobody can prove who was responsible, or when.
  • The network is treated as always-on. Hostels, basements and gates have

  • Notices are broadcast, never tracked: sent to 600, read by 40, no idea
    which 40. (mark this as an illustrative example, not a measured statistic)

appears on slide 3.

SLIDE 6 — WORKS WITH NO SIGNAL, AND WITHOUT A SMARTPHONE
--------------------------------------------------------------------
Headline:   OFFLINE FIRST, AND NO STUDENT LEFT OUT
Sub-head:   The request is created on the device, not on the server.

VISUAL (left: offline diagram, right: kiosk mock):
  LEFT — a two-box diagram: [Device: IndexedDB outbox + idempotency key]
    → (network gap / dotted line) → [Server: /sync/push → dedupe →
    PostgreSQL]. Label the gap "no signal". Show the same operation key
    arriving twice and the second collapsing to the SAME record (draw two
    arrows converging into one row labelled "exactly once").

Bullets (short):
  • Requests are written to the device first, with a device-generated
    idempotency key — the same key can never create a second case.
  • On reconnect the outbox replays; a stale edit returns CONFLICT and never
    silently overwrites.
  • Status is always visible: QUEUED / SYNCING / SYNCED / FAILED_RETRYING /
    CONFLICT.
  • KIOSK: giant touch targets, roll-number lookup, QR scan, auto-reset after
    inactivity.
  • HELPDESK: an operator files on a student's behalf — a normal case with
    source_channel = KIOSK or ASSISTED_DESK, not a lesser workflow.
